# 2026-10-24 - Day 2

Previous day: [[2026-10-23]]

## Checkpoint 0.3b - Corpus cleanup

**Goal:** keep the 2,500 selected Markdown files and remove everything the
corpus does not need, so ingestion works from a small, honest tree.

**What was built**

- `prune_source()` and `prune_corpus()` in `packages/helix/corpus.py`
- `scripts/prune_corpus.py`
- `make corpus-clean`
- Prune tests: selected files kept, unselected files and `.git` removed, missing
  selected file refuses to start, manifest updated
- `Corpus.md`, `README.md`, checklist, and tracing guide updated

**Result**

```text
Pruned corpus: 2500 selected files remain
Removed: 4447 files (plus .git)
Disk: 32.1 MB
```

`data/corpus` went from about **1.8 GB** to **32.1 MB of content** (41 MB
allocated). All 2,500 manifest paths exist; there are no extra Markdown files.
The operation is idempotent: a second run removes 0 files.

**Decision and trade-off**

The manifest paths are relative to each source root, not to `data/corpus`. I
pruned in place inside each source tree instead of copying the selected files
into a new folder, so every manifest path stays valid and there is no second
copy. The cost is that `.git` is gone. Local commands such as `git -C
data/corpus/handbook show ...` no longer work until `make corpus` re-fetches the
checkout. The guide now has commit-pinned GitLab raw/blob URLs for tracing
without a local clone.

`make corpus` treats a source without `.git` as incomplete and re-fetches it.
Run `make corpus-clean` afterward.

**Why not just leave the 1.8 GB checkout?**

Because then "the corpus" is ambiguous: is it the manifest's 2,500 files, or the
whole sparse folder including images, templates, and Git objects? Ingestion must
read the manifest. A clean tree makes that boundary visible and keeps local disk
use small.

## Doubts from 0.3 (answered)

### Is this just data accumulation?

For this checkpoint, yes. RAG has two halves: get trustworthy knowledge in, then
retrieve and reason over it. We are mimicking the first half of an enterprise
knowledge assistant. The sources are public GitLab docs, not private company
data; in production the connectors would point at Confluence, Drive, SharePoint,
or an internal wiki.

### Where does the data live?

`data/corpus/` holds two clean source trees containing only the selected
Markdown, plus `NOTICE`. `data/manifest.json` is the catalog of the selected
2,500 files. `data/` is gitignored; the repository stores the recipe, not the
data.

### How was it downloaded, and how would someone else do it?

I ran `make corpus`, which calls `scripts/fetch_corpus.py`. A new setup does:

```bash
make sync
make corpus
make corpus-clean
```

It needs `git`, network access, `uv`, and disk. The repositories are public, so
no GitLab token, Groq key, or Docker stack is needed.

### Why was the checkout 1.8 GB when the manifest says 32 MB?

Sparse checkout selects folders, not file types. Those folders contained images
and other assets, and the partial clone kept Git objects. The manifest is the
corpus; the checkout was only the working tree. `make corpus-clean` now removes
the extras.

### What is the manifest, and why is it not the same as the checkout?

The manifest is the receipt and the contract: source commit, selected paths,
bytes, words, and estimated chunks. Before cleanup the checkout contained more
files than the corpus. After cleanup it still must not be walked blindly:
ingestion reads the manifest's file list.

### What will the bot answer from?

It will retrieve small chunks from the 2,500 selected documents and ask the LLM
to answer using those chunks with citations. The vector index is built in M1; the
bot does not read the raw corpus at answer time.

### Where do ACLs fit?

The public corpus has no real permissions yet. Later we will assign synthetic
roles to paths (for example, Finance-only or Security-only) and filter before
retrieval. That is M1/M4.

### How do I trace one file and make seed questions?

See [[Tracing-a-Document]]. The Zuora Collect page is in the manifest at 24,786
bytes / 4,011 words; its Git blob hash matches the pinned commit `438cdf82...`.
The first seven seed questions are in `evals/seed_questions.jsonl`, including one
unanswerable SLA question for abstention testing.

## Evals: the ruler before the score

An **eval** is a repeatable test with a dataset, a metric, and a threshold. A
unit test answers "does this function behave?"; an eval answers "is this system
good enough on real questions?" The distinction matters because an LLM can pass
a unit test and still give a confident wrong answer.

The evaluation note covers:

- golden datasets and why they are manual first;
- retrieval metrics: recall@k, MRR, nDCG;
- generation metrics: faithfulness and citation validity;
- end-to-end metrics: task success, latency, and cost;
- security metrics: ACL leaks, prompt injection, PII, and abstention;
- ablations and release gates.

The seed set is seven cases, not the final ruler. It exists to force us to read
the source and agree on what "correct" means before building retrieval.
