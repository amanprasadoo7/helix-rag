## Checkpoint 1.3 - design conversation

The chunker was explained in plain language before implementation: what a chunk
is, why fixed-size cutting fails, the common strategies, and how the corpus
actually looks. The full explanation, worked examples, and the technical
contract are now in [[Chunking]].

The key finding is that the corpus is already finely sectioned: median section
55 words, p75 114, p95 290, p99 567. Only about 4.6% of sections exceed 300
words. Most sections therefore produce one child; chunking is mostly block
packing and long-tail splitting, not uniform 200-400 token windows.

## Decisions

- **Rule A: one small card per section.** Short sections stay small instead of
  being merged with their neighbours. This keeps citations precise; the
  breadcrumb supplies context. Revisit only if retrieval evals show a problem.
- Parent = the parser section; child = a window inside that section, never
  crossing a heading boundary.
- Children target roughly 200-400 tokens (about 150-300 words) with 10-15%
  overlap, taken at sentence boundaries.
- Pack typed blocks, not raw text. Code stays whole. A table stays whole while it
  fits; a larger table splits by rows with the header repeated. A single row over
  the hard maximum is kept whole and flagged.
- Prepend the breadcrumb and section title to the embedding text.
- Chunk ids are content-addressed; ordinals are stored separately.
- Per-document JSON under `data/chunks` plus a summary with the size
  distribution. No timestamps.
- ACLs are inherited from the document at storage time, not recomputed here.

## Checkpoint 1.3 - implementation

**Goal:** split each parsed section into deterministic parent/child chunks
without crossing headings or breaking code.

**What was built**

- `packages/helix/chunking.py`: `ChildChunk`, `ParentSection`,
  `ChunkedDocument`, `ChunkerConfig`, and `chunk_document`.
- `scripts/chunk_corpus.py`: manifest -> `data/parsed` -> `data/chunks`, with
  deterministic per-document JSON and a distribution summary.
- `make chunk` and `make chunk-sample`.
- `tests/test_chunking.py`: 14 tests for section boundaries, overlap, list
  splitting, table rows, whole code blocks, stable ids, duplicates, empty
  sections, descendants, and determinism.

**Verified manually**

```bash
make chunk-sample
make chunk
```

Result: 2,500 documents, 37,614 parents, 38,165 children. Size p50 66, p90 213,
p95 244, p99 384, max 2,174 words. 25,040 children are under 100 words, which is
expected for this heading-heavy corpus. 78 children are oversize: 34 code blocks
and 44 single-row tables. Two runs produced an identical SHA-256 tree. The Zuora
`Accounts` section split into 156 and 210 words with a 10-word overlap.

**Decisions**

- The first full run exposed a 15,065-word GraphQL table. Keeping every table
  whole would overflow the embedding window and be useless for retrieval, so
  tables now split by rows with the header repeated. A single giant row still
  stays whole and is flagged.
- The 2,174-word code block (~2,800 BGE-M3 tokens) is within the model context,
  so code remains atomic.
- Word budgets are the 1.3 proxy; validate against the BGE-M3 tokenizer in 1.4.
