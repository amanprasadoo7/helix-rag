# 2026-10-23 - Day 1

## Checkpoint 0.1 - Walking skeleton

**Goal:** a runnable API with typed config and a liveness endpoint, before any
infrastructure exists.

**What was built**

- `pyproject.toml` with Python 3.12 pinned via `uv`
- `packages/helix/config.py` - settings loaded from `HELIX_*` env vars
- `apps/api/main.py` - `GET /health/live`, `GET /`
- `tests/test_health.py`
- `Makefile` with `sync`, `dev`, `test`, `lint`, `fmt`, `ci`

**Why this shape**

- Config is typed and environment-driven (12-factor). No hardcoded URLs, so the
  same image works locally and in Compose.
- `/health/live` answers one question only: is the process serving? Dependency
  checks belong in `/health/ready` (checkpoint 0.2), because a liveness probe
  that fails on a slow dependency causes restart loops.

**Test**

```bash
make sync
make dev
curl -s localhost:8000/health/live | jq
make test
make lint
```

**Interview angle**

- Liveness vs readiness: liveness = "restart me", readiness = "send me traffic".
- Why typed settings beat `os.getenv` everywhere: validation at startup, one
  source of truth, easy to test.

## Checkpoint 0.2 - Local stack and readiness

**Goal:** Postgres, Redis, Qdrant, and MinIO start with one command, and
`/health/ready` reports each dependency truthfully.

**What was built**

- `infra/docker-compose.yml` with healthchecks, named volumes, and
  localhost-only port bindings.
- MinIO mapped to `9100/9101` because Portainer owns `9000/9001`.
- `packages/helix/health.py` - concurrent checks with 1.5s timeouts.
- `GET /health/ready` - 200 when all dependencies are up, 503 with the failed
  names when one is down.
- Compose targets in the Makefile: `up`, `down`, `reset`, `ps`, `logs`, `ready`.
- Integration test marker and `make test-integration`.

**Verified manually**

- All four containers healthy.
- `make ready` -> 200 with all checks `ok`.
- `docker stop helix-qdrant` -> 503 with `qdrant: down`.
- `docker start helix-qdrant` -> 200 again.
- MinIO console responds on `9101`.

**Notes / caveats**

- MinIO's official images are unavailable; the Compose file uses a pinned
  community mirror for local dev only. Production would use the official
  distribution or managed S3.
- `make reset` deletes volumes. `make down` keeps them.

Full write-up: [[Compose-Stack]]

## Doubts: storage layers and GUIs

- How do I see what is in Postgres? → Adminer at `:8081`, DBeaver desktop, or
  `psql`.
- Why Redis when we already have Postgres and Qdrant? → queue, cache, rate

- Why did `:6333/` look empty? → that is the API metadata endpoint; the UI is
  `/dashboard`.
- Why MinIO? → large raw blobs belong in object storage, not a relational DB or
  a vector index. S3 API gives a clean path to AWS S3/R2.
- GUIs added under the `tools` profile: Adminer (`:8081`) and RedisInsight
  (`:5540`); Qdrant and MinIO already ship UIs.

## Process - checkpoint checklist

**Problem:** the plan is long enough that either the agent or the human can skip
a step (tests, notes, commit, manual verification).

**Decision:** one versioned checklist with two layers:

- a **roadmap** row per checkpoint, and
- a **Definition of Done** for the current checkpoint.

The agent marks implementation, tests, docs, CI, and commit. The user alone
marks `User verified` after replying `pass`. This prevents the agent from
self-certifying a checkpoint.

`make checklist` parses the file and prints the current checkpoint, remaining
items, and roadmap counts. The file is the source of truth; the HTML guide will
be generated from it later.

See [[Checklist]] and [[Foundations#8. Process: definition of done]].

## Checkpoint 0.3 - Corpus fetch and manifest

**Goal:** create a reproducible corpus snapshot before writing any ingestion
code, so chunking and retrieval have a stable input.

**What was built**

- `packages/helix/corpus.py` - source pins, quotas, even-spaced selection,
  Markdown discovery, word/byte stats, and manifest construction.
- `scripts/fetch_corpus.py` - partial clone + sparse checkout + manifest and
  `NOTICE` copy.
- `NOTICE` - MIT / CC BY-SA 4.0 attribution for the two sources.
- `tests/test_corpus.py` - selection, discovery, stats, manifest, and writer.
- `make corpus` and `docs/helix-brain/01-Architecture/Corpus.md`.

**Verified manually**

```bash
make corpus
python3 -c 'import json; m=json.load(open("data/manifest.json")); print(m["totals"])'
```

Result: 2,500 files, 32.1 MB, 3,984,982 words, ~19,925 estimated child chunks.
Handbook: 1,000 files; product docs: 1,500 files. All 2,500 manifest paths exist
on disk. `data/corpus` is about 1.8 GB on disk because the checkout includes
whole folders, non-Markdown assets, and Git objects; the selected Markdown is
32 MB. A Markdown-only cleanup is planned before M1.

**Decisions**

- Pin full 40-character SHAs, not branches. A branch is a moving target.
- Use `--filter=blob:none` plus sparse checkout. The GitLab monorepo is much
  larger than the corpus.
- Quotas by directory, then even spacing within each directory. Taking the first
  N would bias toward alphabetically early paths.
- Keep the corpus out of git. Commit the recipe (`NOTICE`, fetcher, manifest
  schema), not the data.

**Caveat:** the 19,925 number is `ceil(words / 200)`, not the chunker's output.
It estimates child chunks at about 250 tokens and ignores overlap.

Full write-up: [[Corpus]]

## Doubts from 0.3 (answered)

### Is this just data accumulation?

For this checkpoint, yes. RAG has two halves: get trustworthy knowledge in, then
retrieve and reason over it. We are mimicking the first half of an enterprise
knowledge assistant. The sources are public GitLab docs, not private company
data; in production the connectors would point at Confluence, Drive, SharePoint,
or an internal wiki.

### Where does the data live?

`data/corpus/` contains the two checkouts, `data/manifest.json` is the catalog of
the selected 2,500 files, and `data/corpus/NOTICE` carries attribution. `data/`
is gitignored.

### How was it downloaded, and how would someone else do it?

I ran `make corpus`, which calls `scripts/fetch_corpus.py`. A new setup does:

```bash
make sync
make corpus
```

It needs `git`, network access, `uv`, and disk. The repositories are public, so
no GitLab token, Groq key, or Docker stack is needed.

### Why is the checkout 1.8 GB when the manifest says 32 MB?

Sparse checkout selects folders, not file types. Those folders contain images
and other assets, and the partial clone keeps Git objects. The manifest is the
corpus; the checkout is only the working tree. Before M1 we should materialize
only the 2,500 selected Markdown files into a clean folder (~32 MB).

### What is the manifest, and why is it not the same as the checkout?

The manifest is the receipt and the contract: source commit, selected paths,
bytes, words, and estimated chunks. The checkout contains more files than the
corpus. Ingestion must read the manifest's file list, not walk the checkout
blindly.

### What will the bot answer from?

It will retrieve small chunks from the 2,500 selected documents and ask the LLM
to answer using those chunks with citations. The vector index is built in M1; the
bot does not read the raw checkout at answer time.

### Where do ACLs fit?

The public corpus has no real permissions yet. Later we will assign synthetic
roles to paths (for example, Finance-only or Security-only) and filter before
retrieval. That is M1/M4.

### How do I trace one file and make seed questions?

See [[Tracing-a-Document]]. Example: the Zuora Collect page is in the manifest at
24,786 bytes / 4,011 words; its Git blob hash matches the pinned commit
`438cdf82...`. The first seven seed questions are in
`evals/seed_questions.jsonl`, including one unanswerable SLA question for
abstention testing.
